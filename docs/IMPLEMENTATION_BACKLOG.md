# Omoba Player Portal — задачи реализации

Сопутствующий документ: [ТЗ](PLAYER_PORTAL_SPEC.md). Реализация от 15 сентября 2026
находится в этом репозитории и игровой ветке feature/player-portal-2026-09-15.
[Протокол проверки](VERIFICATION.md) отделяет готовый код от приёмки на устройствах.
P0 — первый полезный портал, P1 — расширения; не называть P1 частью готового P0.

Не закрыты полностью: WEB-04/05 — ручное подтверждение в игровом клиенте и
единый пользовательский сценарий; WEB-09 — физические iOS/Android и Safari;
WEB-10 — опубликованные сборки; WEB-12/13 — эксплуатационная приёмка на целевом
сервере. Код этих направлений реализован, автоматические проверки указаны в отчёте.

## P0, этап A: сквозная интеграция

- [x] WEB-01. Сверить текущий main игры/лендинга, зафиксировать исходные версии.
  Уточнить совместимость API/клиента без перезаписи незакоммиченных iPhone-изменений.
  Результат: короткий compatibility record, список новых production зависимостей
  для согласования, структура Next.js/Account API и план миграций.
- [x] WEB-02. Создать самостоятельное Next.js приложение здесь; Rust Account API
  в игровом workspace. Ограниченно выделить общие career-операции без переписывания
  симуляции. Результат: локальный запуск, healthchecks, типизированный `/v1/me`,
  OpenAPI, одинаковые domain-правила игры и API.
- [x] WEB-03. Ввести portal-миграции/роли, разделить migrate/runtime-connect.
  Проверить реальной PostgreSQL: career version 1 сохранена, игровой процесс
  запускается, веб-роль не изменяет результат/рейтинг/XP. Никаких db push в core.
- [ ] WEB-04. Реализовать browser-start pairing и подтверждение в PC/mobile клиенте.
  Не переносить ключ в браузер. Добавить сессии/logout/revoke, bounded HTTPS worker
  и негативные тесты proof/expiry/origin/секретов. Результат: тот же существующий
  account ID, новая строка профиля не создаётся.
- [ ] WEB-05. Реализовать личный обзор и страницу настоящего результата матча.
  Сквозной тест: войти → закончить матч → дождаться settlement → открыть сайт;
  сравнить JSON результата и UI. Это первый продуктовый рубеж, AC02–AC03.

WEB-05 можно сдать как ограниченный пилот с приглашёнными тестерами до остальных
этапов, явно перечислив непроверенные пункты. Это ещё не полный публичный P0:
аналитика, публикация, нагрузка и реальная браузерная проверка остаются в backlog.

WEB-02 и UI-каркас можно вести параллельно по согласованному контракту. Реальный
вход зависит от WEB-03/04; фикстуры UI не заменяют интеграционный рубеж WEB-05.

## P0, этап B: регулярная польза

- [x] WEB-06. История/фильтры/курсоры и read model аналитики. Повторный projector,
  backfill, поздний settlement, nil rating и u64 проходят интеграционные тесты.
  Метрики имеют формулы, выборку и актуальность; практика не выдумывается в БД.
- [x] WEB-07. Друзья/заявки/ник с прежними лимитами и идемпотентностью. Проверить
  изменения в обе стороны между игрой и сайтом; веб не подделывает presence.
- [x] WEB-08. Настройки публикации, ограниченные чужие профили и opt-in поиск.
  Матрица доступа проверяется прямыми API/Action вызовами и двумя браузерами.
  Полный результат чужого матча не становится публичным.
- [ ] WEB-09. RU/EN, адаптация PC/phone, графики/таблицы, accessibility и все состояния
  ошибок. Проверить реальные Safari iOS/Chrome Android и desktop, сохранить снимки.
- [ ] WEB-10. Курируемый каталог сборок и ссылка на кабинет из существующего лендинга.
  Проверить реальные URL/версию/hash; недоступные платформы честно обозначены.

«Фронтенд готов, пока подключены моки» не означает сдачу кабинета.

## Передача работы

Каждый исполнитель получает точный участок и отдельную рабочую ветку/lease в
соответствующем репозитории. Общий API-контракт согласуется перед параллельными
изменениями. В сдаче обязательно указать версии web/API/game, данные/моки,
исполненные тесты и ограничения. Не добавлять production-зависимости, секреты,
инфраструктуру и CI/CD без требуемого в workspace согласования.
